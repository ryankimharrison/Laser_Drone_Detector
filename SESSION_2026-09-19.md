## RESOLVED 2026-09-19: L is measured, and the gain is NOT the problem

`measure_latency.py --wall`, n=16, 0 misses, laser flashed at a plain wall
with the room lit. **Command -> photons visible in a frame: 51.2 ms median**
(sd 7.2; floor 26.27 sd 1.92 -> onset threshold 37.80). Plus ~15 ms inference:

```
LATENCY_S  0.060 ESTIMATE  ->  0.066 MEASURED
ceiling 1/(8L)                 1.89 /s
K = 2.0                        1.06 x ceiling   ABOVE it -- the oscillation
K = 1.2                        0.63 x ceiling   inside it
"back off 30%" target          1.33
```

**K=1.2 is already where the rule of thumb puts it.** Stop tuning gain. The
235 px that remains is something else, and the association gate below is the
measured candidate. The earlier guess in `config.py` ("at a true 90 ms the
ceiling is 1.4") had the direction right and the size wrong -- K=2.0 was over
by 6%, not by half.

Two things that made the wall measurement work, both worth keeping:
- **Detect the dot by GREEN EXCESS, `G - max(R,B)`, not brightness.** The
  projector was only ever supplying a black field for contrast; chroma buys
  that back with the lights on. Checked on synthetic frames with a slow
  brightness drift: brightness put the 6-sigma threshold at 36.7 and the dot
  scored 17.8, a **MISS**; chroma had a 27x margin. A lit wall is neutral, so
  it cannot imitate 532 nm however the light changes.
- **Signed difference, not `absdiff`.** The beam can only push a pixel one
  way. Under chroma an absolute difference lets anything turning REDDER -- a
  hand, a warm reflection -- fire the trigger.

Measured at narrow exposure -6, which is what `app.NARROW_EXPOSURE` uses in
flight, so the integration time inside the number is the real one.

## THE NEXT THING TO DO: the association gate

**Widen or re-seed the tracker's association gate.** Measured on
`diag/flight/run_2026-09-19_012845` (1701 control rows, 190 s):

```
frames the DETECTOR found a target   1245   73.2%
frames a BOX reached the controller   562   33.0%
detected but ASSOCIATION dropped it   683   40.2%   <-- the bottleneck
association survival: 45.1%           (config.GATE_PX = 60)

state       frames   detected   box kept
ACQUIRE        589      83.2%      62.0%
TRACK          450      86.4%      43.8%
COAST          346      78.9%       0.0%     <-- sees it, rejects all of it
SEARCH         316      29.4%       0.0%
```

**In COAST the detector sees the drone on 79% of frames and association
rejects 100% of them.** The turret loses the lock, coasts, its prediction
drifts past the fixed 60 px gate, and it then cannot accept the drone while
looking straight at it -- it has to fall to SEARCH and start over. That is the
hunting behaviour still visible.

Two candidate fixes, not yet tried:
- scale the gate with the filter's own uncertainty (it already tracks `q`),
  so a drifted prediction admits a wider search
- re-seed the filter from a confident detection after a miss streak, instead
  of requiring the new box to match a stale prediction

### The runaway fix (the big one)

`control.compute()` now asks "has a DETECTOR seen this recently?" and:
- **drops the P term** once evidence is stale -- it was the runaway term,
  because the filter keeps extrapolating position so `e` grows on no evidence
- **decays the feedforward to zero** over `COAST_HOLD_MS + COAST_DECAY_MS`,
  applied to the FINAL rate after saturation (scaling the raw demand does
  nothing -- 0.6 x an enormous number still clips to `MAX_MOTOR_RATE`)

Recorded failure it fixes (`run_2026-09-19_011729`): it had the drone centred
and converging, error 111 -> 98 -> 68 -> **45 px** at conf 0.72. One frame
missed, then with NO detection at all the error grew 200 -> 510 px and the
command ramped to **-200 deg/s**, flinging the turret away from a drone it had
just centred. At that rate nothing is detectable, so it never came back.

## KNOWN OPEN

- **Association gate** -- see the top. Biggest remaining loss.
- **1.15x over-travel.** Payload moves 1.15x commanded, consistently
  (spread 0.07 at yaw 0). Real scale error in `AXIS_STEP_DEG` or
  `DIFFERENTIAL_N`. Tracking absorbs it through the measured Jacobian; `level`
  and the travel limits do not.
- **IMU is off the rotation axis.** It reads gravity + `alpha*r` during
  acceleration, so accelerometer tilt is only valid when stopped. `d(tilt)`
  between frames has shown 288 deg/s, above the mechanical limit -- any
  analysis differencing accel tilt during motion is contaminated. Integrate
  the GYRO instead. Exact offset not extracted from CAD.
- **Dead-reckoned pose is 2.2x wrong.** `_integrate_pose` only runs on frames
  that COMMAND (202 of 621 in one run) while the Pico holds the last rate, and
  it applies the new rate over a dt that already elapsed.
- **Face-interlock rotation sign STILL unproven.** `STATUS.md` item 1. The ARM
  check now runs without crashing but has never passed. **Do not arm.**
- **GY-85 lead at J5 comes loose.** Dropped out twice during motion. Fails
  worst mid-move: `level` loses the only thing that can stop it.

## THINGS THAT WOULD HAVE COST ANOTHER NIGHT

- **`imu watch` cannot stream** -- it exits on its own CRLF. Poll `imu` instead.
- **`imu fast`** (fw iter 7) is the cheap read: 2 I2C bursts, ~1 ms. Plain
  `imu` runs a 16-sample liveness check (~160 ms) AND can reconfigure the part
  as a side effect -- never use it for telemetry.
- **Polling a MISSING IMU disables the axes** on every call, and the error text
  bleeds into the next reader's buffer. The attitude sampler now backs off
  after 3 refusals. A monitor must not be able to break what it monitors.
- **Confidence and box size cannot tell the drone from a false positive.** The
  real drone detects down to 0.350 -- the threshold itself -- and spans
  56-482 px. Raising `YOLO_CONF` to 0.55 would discard 28% of REAL detections.
- **Inferring at 1280 while training at 640**: the val split says 640 is
  better, live paired frames say 1280 wins in every size bucket (0.962 vs
  0.796). The val set is close-up footage; the demo is not. Trust live.
